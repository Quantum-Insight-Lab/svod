Храповик: как это сделано

Фактическая реализация СВОДа и ratchet — что лежит в репозитории и как оно работает

версия 0.1стек: Python 3.10+ stdlib git: обязателенстатус приёмки: зелёный

В двух строках

Это спутник документа-замысла. Там — что должно быть; здесь — что реально собрано: два Python-файла без внешних зависимостей, лестница в JSON, append-only журнал и git как механизм отката. Все фрагменты ниже — из настоящего кода и настоящих прогонов.

Главная гарантия в коде: вердикт ступени берётся только из кодов возврата подпроцессов, а лестница не двигается без ручной правки человеком.

§1 Что в репозитории

Семь артефактов. Два из них — исполняемое ядро, остальное — конфигурация, журнал и документация.

svod.py — ядро СВОД: утверждения, провенанс, уверенность, обучение источников
ratchet.py — храповик: оркестратор + арбитр + бегунок по лестнице
ladder.json — лестница ступеней; редактирует только человек
ladder_red_demo.json — заведомо падающая ступень для проверки отката
journal.jsonl — append-only журнал попыток (вне git)
ratchet.cmd — обёртка под PowerShell
README.md / .gitignore — инструкция и исключения

Никаких внешних зависимостей: используются только subprocess, json, argparse, datetime, pathlib. git вызывается через subprocess.

§2 СВОД: модель уверенности

Всё состояние СВОДа — один файл svod.json: источники с надёжностью, темы с утверждениями и плоский список наблюдений «кто что сказал когда». Уверенность утверждения не задаётся, а вычисляется.

Внутри темы конкурирующие версии делят «вес» — сумму надёжностей поддержавших источников. Добавлена фиктивная альтернатива NULL с весом R_INIT = 0.5 — это априорный скепсис, из-за которого одинокое слабое утверждение не дотянет до 1.0, а спорная тема расщепляется вниз.

# уверенность(claim) = вес_поддержки / (R_INIT + сумма_весов_темы)
belief[statement] = sum(rel.get(s, R_INIT) for s in srcs)
denom = R_INIT + sum(belief.values())   # NULL-альтернатива
conf[key] = belief[statement] / denom

Следствия: одинокий источник 0.5 даёт ровно 0.5/(0.5+0.5)=0.5 и никогда не 1.0; консенсус надёжных поднимает версию к ~0.83; спорная тема, где у каждой версии свой слабый источник, садится к ~0.08.

§3 СВОД: обучение надёжности

«Кому верить» и «во что верить» — курица и яйцо. Команда learn N крутит это N раз (truth discovery в духе Sums/Investment): вера в утверждение усиливает доверие к его источникам, и наоборот.

for _ in range(iterations):
    # вера(claim) = сумма доверий поддержавших, нормируем к [0,1]
    belief[key] = sum(trust[s] for s in srcs)
    belief = {k: v / max_b for k, v in belief.items()}
    # доверие(источник) = средняя вера его утверждений
    trust[src] = sum(belief[k] for k in keys) / len(keys)

Пол и потолок (R_MIN=0.05, R_MAX=0.95) не дают надёжности схлопнуться в абсолют. На демо-данных после learn 4: согласные с большинством (alice/bob/dave) растут до 0.88–0.95, контрарные (carol/erin/frank) оседают к полу 0.05.

§4 Храповик: один tick

Команда ratchet tick — конечный автомат с жёсткими воротами. За вызов — максимум одна попытка одной ступени, без цикла по лестнице.

  1. Привести дерево к чистому (снапшот-коммит, если грязное), запомнить текущий коммит как base.
  2. Взять первую ступень со status != shipped.
  3. Если она passed или не approved — напечатать причину и выйти (код 0). Это шлюзы.
  4. Иначе выполнить apply (минимальное изменение), затем checks как реальные подпроцессы.
  5. Зелено (все rc=0) → status=passed, commit «ratchet: ID passed», запись в журнал, СТОП.
  6. Красно → git reset --hard base + git clean -fd, причина в журнал, СТОП. Статус не меняется.

§5 Человеческие шлюзы (собачка)

В коде tick два явных шлюза, и оба просто печатают сообщение и делают return 0, ничего не меняя:

# шлюз №1: пройденная, но не отгруженная — блокирует
if step.get("status") == "passed":
    print("храповик: ступень уже passed. Нужен человек: ship ...")
    return 0
# шлюз №2: без одобрения ничего не делаем
if not step.get("approved", False):
    print("жду одобрения ступени ...")
    return 0

Переход passed → shipped делает только команда ratchet ship <id>, а approved=true — только ручная правка ladder.json. Нет ни одной ветви кода, которая продвигает лестницу автономно.

§6 Гарантии в коде

Песочница

Каждый подпроцесс запускается с cwd = каталог проекта (ROOT). Сетевых вызовов в коде нет. Выйти за пределы каталога нечем.

Версионный контроль

Перед изменением — ensure_clean() (снапшот-коммит, если грязно). Зелёное коммитится, красное откатывается через reset --hard + clean -fd. Личность коммитов задаётся инлайн (-c user.name=ratchet), глобальный git config не трогается.

Ограниченность

В коде нет цикла по ступеням: first_unshipped() берёт ровно одну, каждая ветка завершается return. Цели «довести до канона» не существует — есть конечная лестница.

Никакого самозачёта

Вердикт фазы — ok = all(rc == 0), выводится исключительно из захваченных кодов возврата. Мнение агента вердиктом не является.

§7 Журнал и воспроизводимость

На каждую попытку в journal.jsonl дописывается строка: время, id ступени, git sha (или «откат»), вердикт и захваченный вывод всех команд. Это «СВОД о собственной разработке»: запись = утверждение «ступень работает» с провенансом.

{"time":"2026-05-29T08:51:03+00:00", "step":"T1", "sha":"1dbce02...",
 "verdict":"green", "checks":[{"cmd":"...","rc":0,...}]}
{"time":"2026-05-29T08:51:34+00:00", "step":"BAD", "sha":"откат",
 "verdict":"red", "checks":[..."rc":1,"stderr":"AssertionError"...]}

Команда ratchet verify <id> заново прогоняет checks и сверяет коды возврата и вердикт с последней записью журнала. Расхождение означало бы скрытое состояние.

§8 Приёмка: реальный вывод

Сценарий приёмки самого храповика прогнан на трёх игрушечных ступенях. Ниже — фактический вывод (сокращён).

=== TICK #1: одобрена только T1 ===
храповик tick: ступень T1 — «Сложение»
  [apply] $ python -c "...write('def add...')"   rc=0
  [check] $ python -c "...assert add(2,3)==5"    rc=0
коммит 1dbce02 «ratchet: T1 passed»; статус -> passed.
СТОП. Следующую ступень храповик сам не берёт — нужен человек.

=== TICK на падающей ступени (откат) ===
  [check] $ ...assert VALUE==999   rc=1
    err| AssertionError
откат к 28eb204; рабочее дерево чистое, репозиторий рабочий.

=== verify T1 ===
  текущий вердикт : green  rc=[0]
  журнал          : green  rc=[0]
  СОВПАДАЕТ — вердикт воспроизводим.

Все пять пунктов приёмки пройдены

  • tick трогает ровно одну ступень и останавливается;
  • красная попытка откатывается, репозиторий остаётся рабочим;
  • вердикт воспроизводится повторным прогоном и совпадает с журналом;
  • без одобрения/ship лестница не двигается;
  • в коде нет ветви, перебирающей ступени без человека.

§9 Команды и привязка к OpenClaw

КомандаКтоЧто делает
ratchet tickOpenClawодин удар: попытка одной ступени
ratchet statusчеловексостояние лестницы (read-only)
ratchet ship <id>человекpassed → shipped
ratchet verify <id>человексверить вердикт с журналом
approved=trueчеловекручная правка ladder.json

ratchet tick вешается на сердцебиение/cron OpenClaw: один удар = один tick. Сводку OpenClaw доставляет человеку в чат; человек отвечает одобрением следующей ступени, командой ship или запросом разбора. Так автономный фон не может убежать вперёд — каждый зуб фиксирует человек.

На момент сборки: T1 shipped, T2 passed, T3 pending — лестница ждёт человека.
